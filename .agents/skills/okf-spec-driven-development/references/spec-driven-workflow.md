# 仕様書駆動ワークフロー

## 1. Discovery

`specs/index.md` から対象概念を辿り、`sources` に記された実装・テスト・設定を読む。`rg` でシンボル、Luaコールバック、CTest名、ビルドプリセットを確認し、仕様と実装の差分を「既存挙動」「意図された変更」「未確定」に分ける。

## 2. Specification

変更単位ごとに `specs/changes/<change-id>.md` を作る。`change-id` は小文字の英数字とハイフンで短く保つ。受入条件は正常系、境界、失敗、キャンセル、並行実行、ネイティブ/WASMのうち影響するものを含める。仕様にない互換性やエラー方針を推測で決めず、実装から既定値を確定できない場合は `draft` として残す。

## 3. Test-first implementation

受入条件ごとに既存テストを対応付け、不足する場合は最小の失敗テストを追加する。C++境界はGoogle Test/CTest、Luaの純粋ロジックは既存のテスト実行経路、ドキュメントはOKF構造・リンク検査を使う。テストが通る最小実装の後、外部挙動を変えない範囲で整理する。

## 4. Evidence and synchronization

実装後に対象テスト、GCCビルド、必要ならEmscriptenビルドを実行する。結果が仕様の受入条件を満たすことを確認し、概念の `sources`、`generated.at`、`verified`、`status`、索引、ログを更新する。未検証の仕様は `stable` に昇格させない。互換性を壊す場合は変更仕様に移行手順と明示的な破壊範囲を追加する。

## 5. 完了判定

次をすべて満たしたときだけ変更を完了とする。

- 受入条件がテストまたは構造検証へ一対一に対応している。
- 変更したコードとテストが成功している。
- 影響したOKF概念から実装・テストへ辿れる。
- 新しい挙動、制約、未解決事項が仕様に反映されている。
- スキル検証とMarkdown/YAML検証が成功している。
